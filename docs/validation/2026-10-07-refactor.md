# M1 refactoring validation — 2026-10-07

This run validates archive opening and metadata browsing, not extraction or
compression. All executed checks below ran on Windows x64.

| Configuration | Result |
| --- | --- |
| MSVC 19.51, bundled backend, no Qt | Configure/build and 3/3 CTest suites passed |
| Clang-cl 22.1, C++ targets using the pinned MSVC-built C backend | Configure/build and 3/3 CTest suites passed |
| GCC 16.1, independently compiled bundled backend/codecs, no Qt | Configure/build and 3/3 CTest suites passed |
| Default desktop, MSVC + pinned source Qt 6.10.3 | Full Qt build/install, bundled backend build, application build and 6/6 CTest suites passed |
| Developer desktop, explicitly selected Qt 6.11.2 MSVC kit | Build, frontend tests, qmllint and launch checks passed |

The default desktop suites are `core`, `archive`, `application`, `qt_adapters`,
`qt_home_smoke`, and `qt_filename_rendering`. Archive tests contain 16 cases;
application tests contain 11 cases. They cover generated ZIP/TAR/7z/GZIP and
encrypted ZIP metadata, Unicode, invalid/truncated input, reader limits,
cancellation, bounded queues, completion races, worker exceptions, shutdown,
and immediate directory children. The rendering regression uses production QML
and checks that malicious markup in filenames makes no image requests. A
positive rich-text control verifies that the request observer works.

Additional checks with the default source Qt executable:

- A genuine ZIP renamed to `.data`, containing 25,001 Unicode/emoji entries,
  opened successfully and reported all entries.
- The same ZIP at a native Windows path longer than 260 characters opened
  successfully; the tested path has 388 Unicode code points / 389 UTF-16 units.
- A raw GZIP opened as one entry and displayed its unavailable size as Unknown.
- A ZIP containing literal `<b>` and HTTP/file `<img>` filenames displayed them
  as plain text. No image load errors or external reads were triggered.
- Invalid archive input returned failure with a localized error.
- Desktop launch and archive rendering were checked at 100%, 125%, 150% and
  200% scale using Qt's offscreen platform. These are rendering checks, not a
  physical monitor or screen-reader audit.

All dependencies are pinned by Git gitlinks; the selected Qt modules and Mbed TLS
framework are pinned by their parent repositories. Source checkouts remained
clean. `git diff --check` passed. Project-authored C++ builds had no warnings;
upstream Qt produced deprecation warnings and four C4702 warnings from its
headers in generated QML code, without enabling warnings-as-errors for Qt.

The first source Qt attempt exposed an MSVC generated-object path limit. The
build now uses a shorter default Qt directory and only the Basic controls style
used by the application. The validation cache retained its previous directory
to reuse compiled objects; the source/module pins were unchanged. Nested Qt
component/tool searches now stay on the bundled kit, including on machines with
other Qt kits registered by Qt Creator.

Vulkan-Headers was pinned after optional SDK discovery. All 50 include files
were SHA256-identical to the SDK headers used in the completed Qt compilation.
Those compiled Qt objects were reused; the application and fresh default Qt
builds select the repository's pinned headers. No third-party source was patched
to bypass the build failures.

Linux/macOS CI and sanitizers are configured but were not executed in this run.
Payload CRC validation, secure extraction, archive creation, million-entry UI
performance, 10–100 GB archive benchmarks, portable deployment and installers
remain later milestones. Opening metadata must not be described as proving
payload integrity or safe extraction.
